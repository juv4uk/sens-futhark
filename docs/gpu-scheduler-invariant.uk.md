# Політика ранерів і допуск GPU (#82, #79)

## Чинне правило GitHub Actions

**Всі jobs цього репозиторію мають запускатися на GitHub-hosted runners.**
Персональний WSL/Windows-хост, `self-hosted`, динамічні `runs-on`
та невідомі мітки не є допустимими маршрутами.

Перевірка маршрутизації:

```bash
bash tools/check-gpu-single-lane.sh
```

Назву скрипта збережено для зворотної сумісності. Його поточна роль —
перевірити явні `runs-on: ubuntu-24.04` у всіх workflow та відхилити
локальні чи невизначені маршрути. Додатковий job
`.github/workflows/hosted-runner-routing-policy.yml` перевіряє
`RUNNER_ENVIRONMENT=github-hosted` на реальній машині GitHub.

## GPU — окрема апаратна вимога

1. **Структурний CI ≠ GPU execution.** `make check` або успішне збирання
   Futhark не є доказом виконання CUDA.
2. **SKIPPED = UNVERIFIED.** Якщо апаратний CUDA job не виконався, жодна
   презентація, бенчмарк або release gate не може називати його GPU PASS.
3. Стандартний `ubuntu-24.04` не гарантує NVIDIA GPU. Виділене обладнання
   GitHub-hosted потребує окремого підтвердження наявності та дозволу доступу;
   **жодного fallback на локальну машину**.
4. `nvidia-smi`, CUDA device/toolkit preflight, реальний kernel та артефакт
   із версіями, runner identity, SHA і результатом — окремі обов'язкові свідки.
5. Один фізичний GPU обслуговується узгодженим планувальником, якщо декілька
   задач справді ділять **ту саму** машину. Це правило не означає, що
   різні GitHub-hosted VM мають одну фізичну карту.

## Історичний контекст (не чинне налаштування CI)

Раніше `sens-futhark` виконував CUDA на власній GTX 1050 Ti через
`self-hosted` WSL, з арбітражем `cml#472`. Ці запуски залишаються
історичними доказами для конкретного обладнання, але **не дозволяють**
повертати `runs-on: [self-hosted, ...]` до GitHub Actions.

## Межа доказу

Route guard доводить маршрут job на GitHub-hosted машину; він не доводить
наявність GPU, продуктивність kernel, коректність математичних законів
чи завершену CUDA parity.
