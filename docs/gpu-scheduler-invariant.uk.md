# Інваріант: один планувальник GPU (#82)

## Правило

На **одну фізичну карту — один планувальник**. У межах екосистеми арбітраж однієї карти — за `juv4uk/cml#472`. Новий GPU-шлях або поважає цей арбітраж, або не існує.

У межах цього репозиторію правило таке:

1. **Не більш ніж один** воркфлоу може заявляти GPU-лейн — тобто виконувати CUDA-роботу (`cuda-env.sh`, `--backend=cuda`, `smoke-cuda`, `*-cuda`, `nvidia-smi`) **або** цілити в GPU-лейбли раннера (`gpu`, `cuda-*`, `gtx-*`, `nvidia-*`).
2. Цей єдиний GPU-job мусить цілити в **канонічний self-hosted** воркер — ніколи в hosted (`ubuntu-*`/`windows-*`), бо це тихий фолбек.
3. Диспетчі **обмежені** (bounded): GTX 1050 Ti — display-class WDDM, тож нескінченне spin-ядро спричиняє Windows TDR (скидання драйвера). Жодне ядро не крутиться без межі.

## Перевірка

```bash
bash tools/check-gpu-single-lane.sh
```

Fail-closed: другий GPU-воркфлоу, або GPU-лейн на hosted-раннері ⇒ `exit 2`.

## Чому саме так

Зараз до тієї самої карти ведуть кілька шляхів:

- Actions-джоб `GPU-only CUDA witnesses` (self-hosted, WSL-хост);
- Windows-воркер #77 (IPC, PyTorch);
- `sens` main щойно уніфікував власний GPU-лейн на канонічному CUDA-воркері.

Якщо хтось додасть ще один шлях із власною чергою — карта почне конкурувати сама з собою, і докази стануть недостовірними. Тому інваріант зафіксовано як **перевірний guard**, а не як побажання в документі.

## Non-claim

Guard ловить **статичну** множинність GPU-лейнів у репозиторії. Він **не** доводить, що в рантаймі справді один шедулер — це властивість `cml#472`, а не цього репо.
