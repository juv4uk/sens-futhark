## Steady-state result

| Elements | C median | CUDA median | CUDA/C speedup |
| ---: | ---: | ---: | ---: |
| 1,048,576 | 1,189 µs | 1,365.5 µs | 0.8707× |
| 2,097,152 | 2,378 µs | 2,720.5 µs | 0.8741× |
| 4,194,304 | 5,037 µs | 5,002 µs | 1.0070× |
| 8,388,608 | 9,650 µs | 9,705 µs | 0.9943× |

At 4M elements CUDA has a single median win of about 0.7%, but the 8M result
reverses it. Therefore this run does **not** establish a sustained CUDA
crossover. The two backends are effectively at parity in the 4M–8M region for
this extremely cheap validation workload.

The raw p10/p90 ranges overlap substantially, so claiming a meaningful GPU win
from the 4M point alone would overstate the evidence.

## Cold-start result

For small batches the GPU context dominates. Earlier calibration run
`37342496238` measured the 256-element cold median at approximately:

- C: 1.554 ms
- CUDA: 829.55 ms

The larger-batch evidence run measured cold startup on a 1M-element input at
approximately:

- C: 76.25 ms
- CUDA: 889.81 ms

These are process-level end-to-end cold launches and must not be mixed with the
steady-state Futhark bench medians above.

## Interpretation

For this simple identity-validation kernel on a GTX 1050 Ti:

- GPU offload is clearly counterproductive for small batches.
- Around 1M–2M elements the C backend remains roughly 13–15% faster.
- Around 4M–8M elements C and CUDA converge to parity.
- No sustained GPU advantage is proven yet.

This is a useful negative/neutral result: merely moving SENS-shaped data to the
GPU is not enough. GPU wins should be sought in substantially heavier
data-parallel operations where more work is performed per transferred element.
