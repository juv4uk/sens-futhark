## Steady-state result

| Elements | C median | CUDA median | CUDA/C speedup |
| ---: | ---: | ---: | ---: |
| 1,048,576 | 1,189 µs | 1,365.5 µs | 0.8707× |
| 2,097,152 | 2,378 µs | 2,720.5 µs | 0.8741× |
| 4,194,304 | 5,037 µs | 5,002 µs | 1.0070× |
| 8,388,608 | 9,650 µs | 9,705 µs | 0.9943× |

At 4M elements CUDA has a single median win of about 0.7%, but the 8M result
reverses it. Therefore this run does **not** establish a sustained CUDA
crossover. The two backends are effectively at parity in the 4M–8M region for
this extremely cheap validation workload.

The raw p10/p90 ranges overlap substantially, so claiming a meaningful GPU win
from the 4M point alone would overstate the evidence.

## Cold-start result

For small batches the GPU context dominates. Earlier calibration run
`37342496238` measured the 256-element cold median at approximately:

- C: 1.554 ms
- CUDA: 829.55 ms

The larger-batch evidence run measured cold startup on a 1M-element input at
approximately:

- C: 76.25 ms
- CUDA: 889.81 ms

These are process-level end-to-end cold launches and must not be mixed with the
steady-state Futhark bench medians above.

## Interpretation

For this simple identity-validation kernel on a GTX 1050 Ti:

- GPU offload is clearly counterproductive for small batches.
- Around 1M–2M elements the C backend remains roughly 13–15% faster.
- Around 4M–8M elements C and CUDA converge to parity.
- No sustained GPU advantage is proven yet.

This is a useful negative/neutral result: merely moving SENS-shaped data to the
GPU is not enough. GPU wins should be sought in substantially heavier
data-parallel operations where more work is performed per transferred element.


## Explicit CUDA C-API phase timing

Follow-up Actions run `37346809154` measures the generated CUDA library API
with explicit synchronization at each boundary. Raw artifact:

- artifact ID: `11360224609`;
- artifact zip SHA-256: `93698a33da2b25199913b51deb5bd6070e53ab379bc15d3ae3a8e1312d61f85d`;
- benchmark commit: `7a6fa1f7e3e5affcc9ee02262a5b485314a42c56`.

The phases are deliberately named by the API operation they measure:

- **H→D import** = two `futhark_new_i32_1d` calls + `futhark_context_sync`.
  This includes Futhark device allocation as well as copying two i32 inputs, so
  it is not claimed to be pure PCIe memcpy time.
- **kernel** = `futhark_entry_validate_samples` + sync.
- **D→H export** = `futhark_values_bool_1d` + sync.
- context creation/NVRTC startup is excluded, and a small untimed call warms the
  context before evidence collection.

| Elements | H→D bytes | H→D import median | Kernel median | D→H bytes | D→H export median | Phase sum |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,048,576 | 8,388,608 | 2,925.7 µs | 2,675.2 µs | 1,048,576 | 1,552.9 µs | 7,153.8 µs |
| 4,194,304 | 33,554,432 | 16,242.7 µs | 7,856.4 µs | 4,194,304 | 5,942.7 µs | 30,041.8 µs |

Effective API-phase throughput was about 2.87 GB/s H→D and 0.68 GB/s D→H
at 1M elements, and about 2.07 GB/s H→D and 0.71 GB/s D→H at 4M.

The key observation is structural: for this cheap validator, data import/export
cost is of the same order as, and at 4M substantially larger than, the kernel
itself. This explains why the ordinary C and CUDA backends hover around parity
rather than producing a durable GPU speedup.

The first repetition for each size is retained in `transfer_raw.csv` rather
than discarded. Its larger allocation/import cost is visible in raw evidence;
the table above reports medians across three repetitions.
